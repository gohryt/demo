# Marketplace — второй этап

Go + Fiber v3 + pgx + PostgreSQL. Серверная часть построена поверх первого этапа: каталог и контракт оплаты сохранены, заказ расширен до нескольких позиций. Реализованы задачи 1–4, включая очередь с лимитом и историю состояния.

## Запуск

Нужны Go 1.27+ и PostgreSQL 17+; для демонстрационных скриптов — Python 3 без сторонних пакетов.

```bash
docker compose up -d
go run ./cmd/api
```

Приложение само выполняет версионированные миграции. Существующие заказы, ключи и проводки первого этапа переносятся в новую модель. Миграция выполняется под блокировкой в одной транзакции; повторный запуск не наполняет остатки заново. Во время обновления старую версию API следует остановить.

| Переменная | По умолчанию |
|---|---|
| `DATABASE_URL` | `postgres://marketplace:marketplace@127.0.0.1:5432/marketplace?sslmode=disable` |
| `HTTP_ADDR` | `:8080` |
| `PROVIDER_TIMEOUT` | `2s` |
| `PROVIDER_A_ERROR_RATE`, `PROVIDER_B_ERROR_RATE` | `0`, вероятность отказа до выдачи |
| `PROVIDER_A_TIMEOUT_RATE`, `PROVIDER_B_TIMEOUT_RATE` | `0`, вероятность потери ответа после выдачи |

Заглушки и `/internal/*` предназначены для локального тестового стенда. Реальные платежные системы, проверка подлинности вебхука и авторизация здесь не моделируются.

## API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/orders` | Создать заказ; повтор с тем же `id` и корзиной возвращает существующий |
| GET | `/api/v1/orders/:id` | Позиции, выданные коды, денежные итоги |
| GET | `/api/v1/orders/:id?at=RFC3339` | Состояние на момент времени |
| GET | `/api/v1/catalog?limit=50` | Каталог первого этапа |
| POST | `/webhook/payment` | Вебхук первого этапа |
| POST | `/internal/orders/:id/retry` | Ускорить отложенную попытку; завершенный заказ — успешный no-op |
| GET | `/internal/reconciliation` | Незавершенные заказы, балансы, найденные расхождения с поставщиком |
| GET | `/internal/queue` | Очередь по поставщикам, выданные и возвращенные позиции, расход лимита |
| GET | `/internal/reports?from=RFC3339&to=RFC3339` | Денежные итоги за период из истории |
| PUT | `/stub/providers/a` или `/stub/providers/b` | Режим заглушки и лимит запросов |
| GET | `/health` | Доступность БД |

Несколько товаров, включая повторяющийся SKU:

```bash
curl -sS localhost:8080/api/v1/orders -H 'Content-Type: application/json' -d '{
  "id":"demo-partial",
  "items":[
    {"sku":"STEAM-TOPUP-500","provider":"a"},
    {"sku":"GIFT-ROBLOX-800","provider":"b"}
  ]
}'
curl -sS localhost:8080/webhook/payment -H 'Content-Type: application/json' -d '{
  "event_id":"payment-demo-partial",
  "order_id":"demo-partial",
  "status":"paid",
  "amount":1390,
  "currency":"RUB"
}'
curl -sS localhost:8080/api/v1/orders/demo-partial
```

В начальных данных Steam есть, Roblox отсутствует. Примерно через 8 секунд заказ станет `partially_refunded`: код первой позиции остается доступен, за вторую возвращено 890. `money`: оплачено 1390, выдано 500, возвращено 890, в обработке 0. Суммы целые, в единицах контракта первого этапа: `500` означает 500 RUB.

Старый запрос `{"sku":"STEAM-TOPUP-500"}` работает; для него сохранено переключение A → B. В `items` поставщик закреплен за позицией, по умолчанию A. Максимум 100 позиций, одна валюта. Несколько единиц одного товара задаются повторением позиции. Цена фиксируется при создании. Повтор `id` с другой корзиной дает 409.

Вебхук принимает `event_id`, `order_id`, `status` (`paid`/`failed`), `amount`, `currency`, необязательный `created_at`. Сумма и валюта проверяются, конфликт содержимого одного `event_id` дает 409. Неверная сумма существующего заказа дает 422. Ранние вебхуки хранятся до создания заказа; несоответствующий ранний платеж отмечается `rejection_reason`, деньги не зачисляются. Как в первом этапе, несколько `paid` для одного заказа означают уведомления об **одной оплате**, а не самостоятельные списания.

## Воспроизведение сценариев

Запустить API, затем:

```bash
python3 scripts/stage2.py partial
python3 scripts/stage2.py dishonest
python3 scripts/stage2.py history
python3 scripts/stage2.py burst
```

`BASE_URL` меняет адрес API. Скрипты создают настоящие тестовые заказы и расходуют конечный начальный запас ключей. Для повторяемых проверок без исчерпания запасов используйте интеграционные тесты: у каждого прогона собственная схема и свои данные. Скрипты переключают режимы общих заглушек; запускать их следует последовательно.

`dishonest` проверяет четыре режима, уникальность полученных кодов и денежное равенство. `burst` создает пять оплаченных заказов и один неоплаченный при лимите 2 запроса/минуту; печатает прогресс до завершения, обычно около двух минут. Уже сделанные за последнюю минуту запросы также учитываются.

Настроить поставщика вручную:

```bash
curl -sS -X PUT localhost:8080/stub/providers/a \
  -H 'Content-Type: application/json' \
  -d '{"mode":"error_after_issue","requests_per_minute":60}'
```

| `mode` | Поведение |
|---|---|
| `normal` | Корректная выдача |
| `unavailable` | Отказ без выдачи |
| `duplicate` | Возвращает код другой уже выданной позиции, если такая есть |
| `wrong_sku` | Возвращает код другого товара |
| `error_after_issue` | Сохраняет реальную выдачу, отвечает HTTP 500 |
| `timeout_after_issue` | Сохраняет выдачу и задерживает ответ дольше клиентского таймаута |

После эксперимента вернуть `mode=normal`. Настройки сохраняются в БД и переживают перезапуск.

## Как обеспечивается корректность

**Позиции и деньги.** `order_items` проходят `pending → issuing → delivered` или после трех подтвержденных неудач `refund_pending → refunded`. Между попытками задержка 1, 2, 4 секунды; ограничение запросов не тратит попытки. Для старого одиночного заказа после подтвержденного отказа A выполняется переход на B. Промежуточные статусы заказа первого этапа сохранены. Конечные статусы: `delivered`, `partially_refunded`, `refunded`.

`ledger_entries` содержит положительное `payment_credit` и отрицательные `delivery_debit`/`refund_debit` по позициям. У позиции может быть только одна итоговая проводка. Уникальные ограничения, блокировки строк заказа и отложенные constraint triggers не позволяют зафиксировать лишнюю выдачу, возврат или несбалансированный конечный заказ. Пока обработка продолжается:

```text
paid = delivered + refunded + pending
```

В конечном состоянии `pending=0`, поэтому выполняется требование `paid = delivered + refunded`. При созданном неоплаченном заказе все четыре суммы равны нулю.

**Граница доверия.** `providers.go` моделирует ненадежный ответ посредника. `issuer.go`, `inventory_keys` и `issuer_operations` моделируют независимого доверенного эмитента/реестр активации. Реестр связывает код с SKU, позицией и стабильным `request_id`; код из ответа поставщика напрямую покупателю не передается. «Рабочий код» в рамках заглушки означает действительный код нужного SKU, закрепленный эмитентом за этой позицией. Реальной активации в Steam нет.

Сверка выполняется после каждого ответа, включая 500 и таймаут. Если выдача подтверждена реестром, покупатель получает канонический код. Дубль или чужой код из ответа фиксируется в `provider_discrepancies` с результатом автоматического разбора. Если запрос еще не дошел до эмитента, сверка атомарно записывает окончательную отмену: запоздавший запрос уже не сможет выдать код. Только после подтвержденного отказа допустим новый запрос или возврат.

Без независимой проверки принадлежности/действительности и окончательной отмены невозможно одновременно гарантировать рабочий код, отсутствие повторной выдачи и завершение при поставщике, который лжет во всех каналах. Здесь эта необходимая возможность явно реализована отдельной заглушкой; перенос на реальную интеграцию требует соответствующего контракта эмитента.

**Перезапуск.** Очередь, попытки, запросы эмитента и квитанции возврата находятся в PostgreSQL. Воркер берет позицию через `FOR UPDATE SKIP LOCKED`, сохраняет аренду на `PROVIDER_TIMEOUT + 5s`, освобождает транзакцию, затем выполняет внешний шаг. Повтор использует тот же `request_id`. После истечения аренды другой воркер продолжает обработку; старый ответ не может записать результат благодаря проверке уникального токена аренды. Подтвержденная выдача восстанавливается без нового вызова поставщика.

Возврат — отдельная долговечная заглушка с ключом `refund_{item_id}`. Ее квитанция фиксируется раньше локального завершения позиции. Авария в этом промежутке приводит к чтению той же квитанции. `money.refund_sent` показывает фактически подтвержденные заглушкой возвраты, `refund_unposted` — их еще не отраженную в итоговой проводке часть. Эти состояния также записываются в историю.

**Лимит.** Воркер резервирует разрешение в БД до HTTP-вызова. Все экземпляры используют одну блокируемую строку настроек поставщика. Разрешение учитывается до истечения срока; при поступлении в заглушку оно однократно погашается и занимает слот еще 60 секунд. Просроченное разрешение не позволяет выполнить выдачу. Таким образом, пауза процесса между резервированием и отправкой не сдвигает запрос незаметно в другое окно лимита. Учет скользящий, а не по календарным минутам. Сбой после резервирования может временно снизить пропускную способность, но не увеличивает лимит. Неоплаченные заказы видны в статистике и вообще не расходуют запросы; оплаченные обслуживаются по `paid_at`.

## Проверка денег и истории

```bash
curl -sS localhost:8080/internal/reconciliation
psql "$DATABASE_URL" -f scripts/check_money.sql
```

SQL должен вернуть **ноль строк нарушений**. В JSON у каждого баланса `balanced=true`. Для незавершенного заказа допустим положительный `pending`; это обязательство перед покупателем.

```bash
curl -sSG localhost:8080/api/v1/orders/demo-partial \
  --data-urlencode 'at=2026-09-08T12:00:00+03:00'
curl -sSG localhost:8080/internal/reports \
  --data-urlencode 'from=2026-09-08T00:00:00Z' \
  --data-urlencode 'to=2026-09-09T00:00:00Z'
```

Подставьте время собственного запуска. История — добавляемые снимки бизнес-состояния заказа и денег в `order_history`, записанные в той же транзакции, что и изменение. `at` выбирает последний снимок с `recorded_at <= at`; до появления заказа — 404. Время означает время записи события системой, а не заявленную поставщиком/вебхуком дату и не точный момент PostgreSQL COMMIT. Поздний вебхук не переписывает прошлое. Для заказов первого этапа доступна точная история начиная с миграционного снимка; восстановить отсутствовавшую ранее историю нельзя.

Отчет использует только снимки на границах полуоткрытого периода `[from,to)`, раздельно по валютам. Проверка:

```text
opening_pending + paid = delivered + refunded + closing_pending
```

`UPDATE`, `DELETE`, `TRUNCATE` журналов проводок, истории, квитанций и операций эмитента запрещены триггерами. Это защита на уровне приложения/БД, а не защита от администратора, способного отключить триггеры. Очередь и ее служебные сроки аренды изменяемые; финансовая история — нет.

## Тесты и аварийная остановка

```bash
go test ./cmd/api -count=1 -timeout 180s
go test -race ./cmd/api -count=1 -timeout 180s
go vet ./cmd/api
```

Тесты создают отдельную случайную схему в указанной БД и удаляют ее после прогона; рабочие таблицы не очищаются. Роли БД нужно право создания схемы.

| Сценарий | Проверка |
|---|---|
| Совместимость первого этапа | `app_test.go`: 11 исходных тестов |
| Частичная выдача, повтор оплаты/возврата | `TestPartialRefundAndReplay` |
| Дубль, чужой SKU, 500/таймаут после выдачи | `TestDishonestSupplier` |
| Один SKU несколько раз, несколько воркеров | `TestRepeatedSKUAndConcurrentWorkers` |
| Сбой после выдачи эмитентом, устаревший воркер | `TestRestartAfterIssuerCommit` |
| Сбой после возврата денег, до завершения позиции | `TestRestartAfterRefundCommit` |
| Поздний запрос после окончательной отмены | `TestCancellationFencesLateIssue` |
| Лимит, очередь, приоритет оплаты | `TestRateLimitQueueAndPaidPriority` |
| Истечение и повтор разрешения | `TestPermitExpiryAndReplay` |
| Состояние на дату, отчет, запрет перезаписи | `TestHistoryAndPeriodReport` |
| Неверная оплата, конфликт идемпотентности | `TestPaymentValidationAndIdempotencyPayload` |
| Обновление существующей БД первого этапа | `TestMigrationFromStageOne` |
| Отказ БД фиксировать неверный баланс | `TestDatabaseRejectsUnbalancedTerminalState` |

Тесты перезапуска детерминированно останавливаются между двумя коммитами, создают новый экземпляр приложения и проверяют восстановление только из БД. Тест очереди сдвигает исключительно тестовые записи времени, чтобы не ждать две минуты; `scripts/stage2.py burst` проверяет ожидание в реальном времени.

Аварийное завершение процесса вручную:

```bash
go build -o /tmp/marketplace-api ./cmd/api
/tmp/marketplace-api &
api_pid=$!
# В другом терминале включить timeout_after_issue и запустить сценарий/оплату.
kill -9 "$api_pid"
/tmp/marketplace-api
```

Повторно получите тот же заказ через GET. После истечения аренды он завершится с прежним кодом или квитанцией возврата. Убивать нужно собранный процесс API: `go run` запускает дочерний процесс, поэтому завершение самого `go run` не является надежным тестом аварии сервера.

## Что осталось от первого этапа

Каталог, исходные данные, HTTP-стек и прямые SQL-запросы сохранены. Индекс витрины `products_vitrine_idx (available_count DESC, sku) INCLUDE (name, type, price, currency)` и 5000 нагрузочных SKU остаются. Заглушка эмитента меняет остаток атомарно с резервированием ключа. Внешняя очередь и дополнительный брокер не требуются.

Для демонстрации все компоненты находятся в одном процессе и одной БД. Код проверки эмитента выделен отдельно, но физически независимым сервисом не является. Очередь надежна при нескольких экземплярах; бесконечная недоступность самой БД, как и любой системы хранения, не дает гарантии завершения до восстановления доступа.

## Фактическая проверка

Проверено 8 сентября 2026 на Go 1.27.1 и локальном PostgreSQL 18.6:

- Все 23 интеграционных теста прошли с `-race`, включая 11 тестов первого этапа; итоговый прогон — 12,7 секунды.
- `go vet ./cmd/api` и `git diff --check` прошли.
- Скрипты `partial`, `dishonest`, `history`, `burst` выполнены против запущенного API.
- Реальный всплеск: 5 выдач за 120,34 секунды, максимум **2 запроса в любом скользящем минутном окне**, очередь опустела, неоплаченный заказ остался без выдачи.
- Реальный `SIGKILL` после коммита эмитента, до локального завершения: после запуска нового процесса выданы ровно 2 ключа, первый код сохранен, `paid=delivered=1500`.
- `scripts/check_money.sql` на данных демонстрационных заказов вернул 0 нарушений.

Docker текущему пользователю среды был недоступен, поэтому PostgreSQL для этих проверок запускался отдельно. Конфигурация Docker с PostgreSQL 17 из первого этапа сохранена.
